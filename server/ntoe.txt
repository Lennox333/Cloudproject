## 🔹 Current Situation You Described

* **1 upload** (say `video.mp4`)
* **1 instance** (2 vCPUs)

  * Runs **3 FFmpeg processes** (360p, 480p, 720p)
* **1 API server** (Express) on the same instance
* The **720p transcode** hogs CPU and pushes usage above 70% → instance freezes

So the issue: all 3 transcodes are competing for the same machine.

---

## 🔹 Why Scaling Won’t Work Here

If you keep **all 3 transcodes on the same instance**, then:

* Auto Scaling looks at CPU usage per instance.
* It can spin up more instances, but your current instance is still overloaded because it runs all jobs at once.
* You don’t really get “distribution” — just replication of the bottleneck.

---

## 🔹 Correct Way to Scale (Job Splitting)

Instead of **1 instance = all 3 jobs**, you split each resolution into **separate jobs**.

### Example Flow:

1. **Upload video** → API server (or S3).
2. **API/Lambda** → sends **3 messages** into SQS:

   * Job 1: `video.mp4 → 360p`
   * Job 2: `video.mp4 → 480p`
   * Job 3: `video.mp4 → 720p`
3. **Workers (ECS/EC2 Auto Scaling Group)**:

   * Instance A picks up the 360p job.
   * Instance B picks up the 480p job.
   * Instance C picks up the 720p job.

Now **each worker handles one FFmpeg process** at a time.

* CPU stays <70% per worker.
* If queue fills up, Auto Scaling spins up more instances.
* Express API never freezes, because it only manages job submission.

---

## 🔹 Scaling Trigger Example

* **Scaling Metric = Average CPU** across the Auto Scaling Group.
* Scenario: 5 videos uploaded → 15 jobs in SQS.
* 1 worker is not enough → CPU spikes >70%.
* Auto Scaling adds workers (up to 3 in your assignment).
* Jobs get spread out (e.g. 5 × 720p jobs might each go to different instances).

---

## 🔹 Key Insight

Scaling only works if **each instance runs fewer jobs**, not all jobs.
That’s why **job splitting by resolution (360/480/720)** is essential.

## 🔹 Step-by-Step Flow

1. **Initial State**

   * 1 instance is running your **API server** (Express).
   * 1 worker instance is available for FFmpeg jobs.

2. **First Upload**

   * User uploads a video → API splits into **3 jobs** (360p, 480p, 720p).
   * These jobs go into **SQS**.
   * The single worker instance takes them (sequentially or in parallel if CPU allows).

   👉 At this point, **load distribution** is happening — SQS makes sure jobs are assigned fairly to available workers.

3. **More Uploads Arrive**

   * 5 more videos uploaded → 15 jobs in the queue (5 × 3 resolutions).
   * Now the **1 worker instance** is overwhelmed → CPU goes above 70% and queue backlog grows.

4. **Auto Scaling Triggered**

   * CloudWatch detects **high CPU utilisation** (or too many jobs in queue).
   * **Auto Scaling Group** launches more worker instances (e.g. up to 3).
   * Now multiple workers pull jobs from SQS and process them in parallel.

   👉 This step — **automatically starting new worker instances based on load** — is what we call **Auto Scaling**.

5. **Scale In (Back Down)**

   * When uploads slow down and the queue is empty + CPU <30%, Auto Scaling terminates extra workers.
   * System returns to 1 worker.

---

## 🔹 Key Distinction

* **Load Distribution (SQS):** Decides *where each job goes* (one job → one worker).
* **Auto Scaling:** Decides *how many workers exist* at any given time.

---

✅ So yes:

* Assigning jobs to multiple workers (via SQS) = **Load Balancing**.
* Spinning up extra workers when CPU >70% or queue is big = **Auto Scaling**.

import { ECSClient, ListTasksCommand } from "@aws-sdk/client-ecs";

const ecsClient = new ECSClient({ region: process.env.AWS_REGION });

async function isWorkerRunning() {
  const data = await ecsClient.send(new ListTasksCommand({
    cluster: "my-cluster",
    serviceName: "worker-service",
    desiredStatus: "RUNNING"
  }));
  return data.taskArns && data.taskArns.length > 0;
}
